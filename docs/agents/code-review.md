## 1. Что проверять

### 1.1 Жёсткие ограничения (BLOCKER при нарушении)

- Нет `android.permission.INTERNET`, аналитики, crash-репортеров, рекламы, remote config, синхронизации.
- OCR — **bundled on-device** (`com.google.mlkit:text-recognition`), не Play Services dynamic download.
- Данные только на устройстве (Room/DataStore), без облака и авторизации.
- Прототип: один экран, **до 5 товаров**. История сравнений не реализована.
- Все пользовательские строки в `res/values/strings.xml`, не хардкод в Composable.
- Не добавлены тяжёлые/необоснованные зависимости; новые версии — только в `gradle/libs.versions.toml`.
- В коммит не попали `build/`, `.gradle/`, `local.properties`, `.idea/`.

### 1.2 Архитектура

- `domain` — чистый Kotlin. Запрещены импорты `android.*`, `androidx.*`, `com.google.mlkit.*`, Room, Hilt.
- `data` зависит от `domain`, но не от `ui`.
- `ui` разговаривает с `domain` через use case/интерфейсы, а не напрямую с Room/ML Kit.
- Интерфейсы репозиториев лежат в `domain/repository`, реализации — в `data/repository`.
- Hilt-модули в `di`, нет зависимостей, созданных «вручную» там, где должен быть DI.
- Новый файл лежит в правильной папке; `docs/structure.md` обновлён, если добавлялась папка/модуль.

### 1.3 Корректность

- Парсер ценника и расчёт цены за единицу — чистые функции; нет побочных эффектов.
- Единицы: 1 кг = 1000 г, 1 л = 1000 мл. Нет перепутывания кг/л, г/мл.
- Цена и количество не могут быть нулевыми/отрицательными; есть защита от деления на ноль.
- Денежные значения считаются через `BigDecimal`, сравнение — по числу, а не по строке.
- Округление и форматирование для ₽/кг и ₽/л консистентны.
- `ImageProxy` обязательно закрывается (`close()`) после извлечения кадра.
- Камера привязана к lifecycle, разрешения запрошены и обработаны.
- Состояние экрана — одна immutable `UiState`; эффекты уходят через `UiEvent`/`SharedFlow`.
- Лимит в 5 элементов проверяется и в use case, и в ViewModel.
- Ошибки распознавания превращаются в понятные пользовательские состояния, без падения.

### 1.4 Compose / UI

- Нет захардкоженных текстов и размеров там, где нужны ресурсы/токены темы.
- Список карточек использует стабильные ключи; нет лишних рекомпозиций.
- Стиль «мягкий, округлый, без выебонов»: карточки, скругления, air, крупные цифры цены.
- Кнопки и состояния доступны (контраст, размер текста, область нажатия) — базовый уровень, без фанатизма.

### 1.5 Данные и приватность

- Entity ↔ domain маппинг явный, без утечки Room-типов в domain.
- Для будущей истории таблицы связаны внешним ключом, но история не торчит в UI.
- В логи не пишутся сырые изображения/персональные данные; если `sourceText` сохраняется — это осознанно.

## 2. Формат отчёта

Сначала одна строка вердикта:

- `APPROVE` — блокеров и мажоров нет;
- `CHANGES REQUESTED` — есть что править.

Затем таблица:

| Severity | File:line | Проблема | Как исправить |
| --- | --- | --- | --- |

Severity:

- **BLOCKER** — нарушение жёсткого ограничения, краш, потеря данных, сеть, не работает офлайн.
- **MAJOR** — ошибка логики, нарушение слоёв, неверные единицы/округление, отсутствие обработки ошибки.
- **MINOR** — именование, стиль, мелкая неконсистентность.
- **NIT** — необязательное улучшение.

В конце — короткий чек-лист: какие пункты из раздела 1 ты проверил и что не смог проверить.

## 3. Чего НЕ делать

- Не переписывать код и не коммитить изменения.
- Не ставить `APPROVE` только потому, что «код есть» или «тесты зелёные».
- Не делать выводов без доказательства: указывай файл и строку.
- Не проверять сеть/не запускать внешние сервисы.
- Не требовать идеала в NIT-раундах: блокируй только BLOCKER/MAJOR.
- Не подменять это ревью тестов: качество тестов проверяет отдельный сабагент по `docs/agents/test-review.md`.
- Если это 5-я итерация ревью, а `BLOCKER`/`MAJOR` остались — верни `CHANGES REQUESTED` и отдельно напиши: «лимит ревью исчерпан, нужна эскалация пользователю».
