# AGENTS.md — правила работы с репозиторием

Этот файл — обязательный вход для любого агента или разработчика, который пишет код здесь.
Прочитай его целиком перед изменениями. При расхождении с остальными документами доверяй этому файлу и `docs/architecture.md`.

## 1. Что мы делаем

Offline-first приложение для Android: пользователь фотографирует ценник в магазине,
приложение распознаёт текст, вычисляет цену за 1 кг / 1 л и позволяет сравнить **до 5 товаров**
на одном экране. Авторизации, регистрации, аккаунтов и облака нет.

## 2. Жёсткие ограничения (не нарушать без явной просьбы)

- **Никакого интернета.** Не добавлять разрешение `android.permission.INTERNET`, аналитику,
  crash-репортеры, рекламу, remote config, синхронизацию, загрузку моделей по сети.
  Модель OCR должна быть **bundled on-device** (не через Play Services dynamic download).
- **Все данные остаются на телефоне.** Хранение — только Room / DataStore в `$applicationId`.
- **Прототип = один экран сравнения**, до 5 позиций. История сравнений — отдельная future-задача,
  в прототипе её не реализовывать, но схему БД проектировать с расчётом на неё.
- **Интерфейс на русском языке.** Все пользовательские строки — в `res/values/strings.xml`,
  не хардкодить текст в Composable.
- Не добавлять тяжёлые зависимости «на всякий случай». Каждая новая библиотека должна быть
  обоснована в `docs/architecture.md` и зафиксирована в `gradle/libs.versions.toml`.
- Не коммитить `build/`, `.gradle/`, `local.properties`, `.idea/`, сгенерированные файлы.

## 3. Стек (ориентир)

| Слой | Выбор |
| --- | --- |
| Язык | Kotlin |
| UI | Jetpack Compose + Material 3 |
| Камера | CameraX (`Preview` + `ImageCapture`) |
| OCR | Два on-device движка: Tesseract4Android `rus` (слова/вес/копейки) + RapidOCR AAR (рубли); модели bundled, без сети |
| Фон | Coroutines + Flow, `viewModelScope` |
| DI | Hilt |
| БД | Room (+ Converter для decimal/unit) |
| Настройки | DataStore Preferences |
| Тесты | JUnit 5 + Truth, Turbine для Flow; Compose UI-тесты — по необходимости |
| Сборка | Gradle Kotlin DSL + Version Catalog (`gradle/libs.versions.toml`) |

Версии зависимостей **только** в `gradle/libs.versions.toml`. В `build.gradle.kts` не писать literal-версии.

## 4. Архитектура и направление зависимостей

```
ui  ──▶  domain  ◀──  data
```

- `domain` — чистый Kotlin: модели, парсер ценника, use case-ы, интерфейсы репозиториев.
  **Не зависит** от Android SDK, Compose, Room, Hilt, OCR-движков.
- `data` — реализации: Room, DataStore, CameraX-контроллер, обёртки Tesseract/RapidOCR, репозитории.
- `ui` — Compose-экран, ViewModel, state. ViewModel разговаривает только с use case-ами/репозиториями.
- Парсер и расчёт цены за единицу — **чистые функции**, покрываются юнит-тестами обязательно.

## 5. Структура

Полное дерево и правила «куда класть новый файл» — в [`docs/structure.md`](docs/structure.md).
Кратко: `core/design` (тема и общие компоненты), `data/*` (инфраструктура), `domain/*` (логика),

## 6. Процесс выполнения этапа

Полный план зафиксирован в [`docs/plan.md`](docs/plan.md). Каждый этап выполняется в отдельной
ветке `stage/<NN>-<slug>`, созданной от актуального `main`. Напрямую в `main` код не пишется.

Порядок внутри этапа (не менять):

1. **Реализация кода** в ветке этапа.
2. **Ревью кода** — `general`-сабагент по `docs/agents/code-review.md`, передать diff изменений.
3. **Написание тестов** на изменённую логику.
4. **Ревью тестов** — `general`-сабагент по `docs/agents/test-review.md`, передать diff тестов и код.
5. **Успешный запуск проверок:** `./gradlew :app:assembleDebug`, `./gradlew test`, `./gradlew lint`,
   `./gradlew :app:connectedDebugAndroidTest` (на устройстве или эмуляторе).
6. **Закрытие этапа:** merge ветки в `main`, удалить ветку, `git push origin main`.
7. **Публикация версии:** полноценный этап считается закрытым только после публикации
   GitHub Release с APK, собранным из слитого `main` (см. ниже).

Локальные проверки разрешается гонять и раньше, но финальный зелёный прогон — **после** всех ревью.

### Публикация версии

- Полноценный этап (изменения кода/ресурсов, влияющие на APK) завершается публикацией новой
  версии на GitHub Releases. Документальные правки без изменения APK публикации не требуют.
- APK собирается из `main` **после** merge: `./gradlew :app:assembleDebug`. В релиз загружается
  `app/build/outputs/apk/debug/app-debug.apk` под понятным именем вида
  `PriceLens-stage<NN>-<slug>-debug.apk`.
- Тег релиза — `stage-<NN>-<slug>`; в описании перечислить пользовательские изменения,
  результаты всех проверок и **SHA-256 APK**.
- Ссылка на релиз и хеш APK указываются в финальном отчёте пользователю: скачиваемая версия
  должна появляться сразу после закрытия этапа, а не по отдельному запросу.

### Регресс на эмуляторе

- Регресс этапа обязан включать instrumented-тесты на реальном устройстве или эмуляторе:
  JVM-прогон не заменяет проверку камеры, OCR и Android-контекста.
- Эмулятор поднимается **только для прогона тестов** и выключается сразу после него
  (`adb emu kill`), не оставаясь запущенным «на всякий случай».

### Ограничение на ревью

- Не более **5 итераций** на каждый вид ревью: код и тесты считаются отдельно.
- Если после 5-й итерации остались `BLOCKER`/`MAJOR` — этап **не закрывается**: агент останавливается
  и отдаёт пользователю отчёт с оставшимися замечаниями. Слияние в `main` запрещено.
- Каждое замечание получает реакцию: исправлено или явно обосновано. Для `BLOCKER`/`MAJOR`
  обоснование не принимается — только фикс.
- `MINOR`/`NIT` можно вынести в follow-up, но они перечисляются в отчёте.
- Ревьюер не правит код и не коммитит — только отдаёт отчёт с `file:line` и предложением фикса.

Если добавил модуль/папку — обнови `docs/structure.md` **до** ревью.

## 7. Стиль кода

- Именование: `UpperCamelCase` для классов, `lowerCamelCase` для функций/переменных,
  `snake_case` для файлов ресурсов.
- Состояние экрана — одна immutable data class `UiState` на ViewModel; эффекты (например, «открыть камеру») — через `UiEvent`/`SharedFlow`.
- Не хранить `Bitmap`/`ImageProxy` в ViewModel дольше, чем нужно: распознал → извлёк текст → освободил `ImageProxy.close()`.
- Комментарии только там, где код неочевиден (например, эвристики парсера ценников).
- Коммиты: `feat:`, `fix:`, `chore:`, `docs:`, `test:`, `refactor:`.

## 8. Что НЕ делать без обсуждения

- Добавлять сеть, авторизацию, аналитику, историю как отдельный экран.
- Менять дизайн-систему резко: стиль «мягкий, округлый, без выебонов» — см. `docs/product.md`.
- Переписывать парсер без юнит-тестов на реальных форматах ценников (`docs/ocr-notes.md`).
- Переименовывать пакет/приложение без одновременного обновления `namespace`, `applicationId`, всех docs и AGENTS.md.
